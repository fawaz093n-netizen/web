Prototyping against a local Postgres is the easy part; the awkward step is moving the working app to a hosted database. This guide is the checklist for that move: take a Prisma project running on Docker Postgres or a local `prisma dev` instance, and land it on [Prisma Postgres](https://www.prisma.io/docs/postgres), a managed PostgreSQL database, with the schema, data, and migration history intact. The whole transition is five steps, and the only change your application sees is one environment variable.

## The local-to-production gap

Every Prisma project starts the same way: a schema, a local database, and a tight iteration loop. The trouble starts when the app is ready for other people. Production needs a database that is not your laptop, and most tutorials end right before the part where the data has to live somewhere real.

The move is smaller than it looks. Your schema does not change. Your queries do not change. Prisma Client does not change. Three things move: where the database runs, the connection string that points at it, and the schema and data that have to arrive there. As a checklist:

1. Develop against a local database, with `prisma dev` or Docker.
2. Create the hosted Prisma Postgres database.
3. Point your config at it.
4. Replay the schema, and move the data if it matters.
5. Validate, deploy, and keep the local loop.

The rest of this post walks through each step with the exact commands.

## Start local: `prisma dev` or Docker

The classic local setup is [Docker](https://www.docker.com). You write a compose file, pick a port, mount a volume so data survives restarts, and start the container:

```yaml
# docker-compose.yml
services:
  postgres:
    image: postgres:17
    ports:
      - "5432:5432"
    environment:
      POSTGRES_PASSWORD: postgres
    volumes:
      - pgdata:/var/lib/postgresql/data
volumes:
  pgdata:
```

```text
# .env
DATABASE_URL="postgresql://postgres:postgres@localhost:5432/postgres"
```

This works, and if you already have it, keep it: the rest of the checklist is identical. But it carries baggage that has nothing to do with your app. Docker Desktop has to be installed and running. The compose file has to be maintained. Port 5432 collides the moment a second project does the same thing. And the whole arrangement exists to run one process.

The lighter route is `prisma dev`, which ships with the Prisma CLI:

```bash
npx prisma dev
```

That one command starts a local Prisma Postgres instance, powered by [PGlite](https://pglite.dev), an embedded Postgres engine. There is no daemon to install, no image to pull, and no container to manage. When the server is up, it prints connection strings ready to paste into `.env`:

```text
✔  Your local Prisma Postgres server default is now running

🔌 To connect with Prisma ORM use the following connection strings:

   DATABASE_URL="postgres://postgres:postgres@localhost:51214/template1?sslmode=disable&connection_limit=10&..."
```

Compared to the Docker setup, `prisma dev` is easier on four counts:

- **Zero infrastructure.** No Docker daemon, no compose file, no volumes, no port mapping. Node.js 20+ is the only requirement.
- **Per-project instances.** `npx prisma dev --name myapp` gives every project its own named database with a stable connection string, so nothing collides.
- **A built-in lifecycle.** `npx prisma dev --detach` runs the server in the background, `prisma dev ls` lists your instances, and `prisma dev stop` and `prisma dev rm` shut down and delete them. No orphaned containers, no stale volumes.
- **The same target in both places.** Local `prisma dev` and hosted Prisma Postgres are the same product, so the move this post describes shrinks to a URL swap instead of a platform change.

It speaks standard Postgres on the wire, so `psql`, GUIs, and every Postgres driver connect to it like any other database. The honest trade-offs: the local server accepts one connection at a time (additional connections queue instead of running in parallel), and it is a development tool, ideal for iteration and tests rather than something you self-host. The [local development docs](https://www.prisma.io/docs/postgres/database/local-development) cover the full instance-management reference.

Whichever route you chose, finish the local loop by creating the schema and seeding:

```bash
npx prisma migrate dev
npx prisma db seed
```

From here, both starting points follow the same checklist.

## Create the hosted database

Create the production database in the [Prisma Console](https://console.prisma.io):

1. Open the Console and click **New project** in your workspace.
2. Name the project, click **Get started** under Prisma Postgres, and pick the region closest to your users.
3. Click **Create project**. The database provisions in a few seconds.

Then grab the connection strings you will need:

1. Open the **Connection Strings** tab in the project sidenav.
2. Click **Create connection string**, name it, and copy the result.

You will use this string in two forms: as the `DATABASE_URL` your app reads, and as the `postgres://` [direct connection](https://www.prisma.io/docs/postgres/database/connecting-to-your-database) string that standard Postgres tools like `pg_restore` use in the next steps.

Two CLI alternatives, depending on where you are: for a brand-new project, `npx prisma init --db` scaffolds the schema and provisions a Prisma Postgres database in one go, and [`npx create-db@latest`](https://www.prisma.io/docs/postgres/npx-create-db) creates a temporary database with no sign-up that you can claim and keep when it proves out.

## Update env and config

Point the app at the hosted database by swapping one value:

```text
# .env (before)
DATABASE_URL="postgres://postgres:postgres@localhost:51214/template1?sslmode=disable&..."

# .env (after)
DATABASE_URL="postgres://USER:PASSWORD@db.prisma.io:5432/?sslmode=require"
```

Then regenerate Prisma Client so everything picks up the new configuration:

```bash
npx prisma generate
```

That is the entire application change. No query rewrites, no driver swap, no schema edits.

In practice you will not edit `.env` in place: keep the local URL in `.env` for development, and set `DATABASE_URL` in your hosting platform's environment settings (Vercel, Railway, Fly, or wherever the app deploys) for production. The production connection string is a credential; it belongs in your platform's env config, never in git.

## Move the schema and the data

There are two situations, and they need different commands.

**Starting fresh in production.** If your local data is disposable prototype data, replay the migration history against the hosted database and reseed. With `DATABASE_URL` pointing at Prisma Postgres:

```bash
npx prisma migrate deploy
```

```text
2 migrations found in prisma/migrations

Applying migration `20260710142233_init`
Applying migration `20260722091502_add_posts`

All migrations have been successfully applied.
```

`migrate deploy` is the production counterpart of `migrate dev`: it applies the committed migration files in order and does nothing else, no schema drafting, no prompts, no drift heuristics. That makes it safe to put in CI or your deploy pipeline, which is where it should end up. The [development and production workflows docs](https://www.prisma.io/docs/orm/prisma-migrate/workflows/development-and-production) explain the split. If you have a seed script for production defaults, run it once with the production URL set.

**Bringing the data along.** If the local data matters, copy it with the standard Postgres tools. This works identically whether the source is Docker Postgres or a local `prisma dev` instance, because both accept direct `postgres://` connections. One caveat for `prisma dev`: it allows one connection at a time, so stop your dev server and Studio before dumping.

Export from the local database (use your local connection string):

```bash
pg_dump \
  -Fc \
  -v \
  -d "postgresql://postgres:postgres@localhost:5432/postgres" \
  -n public \
  -f db_dump.bak
```

Import into Prisma Postgres using the direct connection string:

```bash
pg_restore \
  -d "postgres://USER:PASSWORD@db.prisma.io:5432/postgres?sslmode=require" \
  -v \
  ./db_dump.bak
```

Two details worth knowing. First, Prisma Postgres runs PostgreSQL 17, so your `pg_dump` and `pg_restore` need to be version 17 as well; check with `pg_dump --version`. Second, the dump includes the `_prisma_migrations` table, so your migration history arrives with the data and the hosted database starts with a clean, complete record. No separate `migrate deploy` is needed for the initial state. The [PostgreSQL import guide](https://www.prisma.io/docs/prisma-postgres/import-from-existing-database-postgresql) covers this flow end to end, including provider-specific connection notes.

If you develop with `prisma dev` and prefer clicking over dumping, the [Prisma VS Code extension](https://marketplace.visualstudio.com/items?itemName=Prisma.prisma) has a push-to-cloud action that moves a local database to a remote Prisma Postgres instance directly.

## Validate before you switch

Do not declare victory on a successful restore. Four checks, a few minutes total:

1. **Migration status.** Run `npx prisma migrate status` against the hosted database. You want the confirmation that the schema matches the migration history:

   ```text
   Database schema is up to date!
   ```

2. **Row counts.** Spot-check that the data arrived. Open the **Studio** tab in the Console to browse the hosted data, or run a count against the direct connection:

   ```bash
   psql "postgres://USER:PASSWORD@db.prisma.io:5432/postgres?sslmode=require" \
     -c 'SELECT count(*) FROM "User";'
   ```

3. **Smoke test.** Start the app locally with the production `DATABASE_URL` and click through the flows that read and write. Queries behave the same; you are verifying config, not code.

4. **Deploy.** Set `DATABASE_URL` in the hosting platform, add `npx prisma migrate deploy` to the deploy pipeline so future migrations apply automatically, and ship.

Then keep the loop you started with: iterate locally against `prisma dev` with `migrate dev`, commit the migration files, and let the pipeline replay them in production. When you are done with the old local database, `docker compose down -v` or `npx prisma dev rm` clears it away.

## Frequently asked questions

<Accordions type="single">
  <Accordion title="Do I have to move my local data to production?">
Only if it matters. Prototype data is usually better left behind: run `npx prisma migrate deploy` against the hosted database to recreate the schema from your committed migration files, then reseed. Copy the data with `pg_dump` and `pg_restore` when it is real: content you authored, imported records, or anything users would miss.
  </Accordion>
  <Accordion title="Does my application code change when I move to Prisma Postgres?">
No. The schema, the generated client, and every query stay the same. The application-side change is the `DATABASE_URL` environment variable plus one `npx prisma generate`. That is the point of developing against local Prisma Postgres: local and hosted are the same product behind the same connection string variable.
  </Accordion>
  <Accordion title="What happens to my migration history when I import with pg_dump?">
It travels with the data. Prisma Migrate records applied migrations in a `_prisma_migrations` table inside your database, and a schema-level dump includes it. After the restore, `npx prisma migrate status` reports the hosted database as up to date, and future `migrate deploy` runs continue from the same history.
  </Accordion>
  <Accordion title="Should I keep using prisma dev after production exists?">
Yes, that is the intended workflow. Production traffic hits hosted Prisma Postgres while daily development stays on a local `prisma dev` instance: free, fast, and disposable. Schema changes flow one way, from `migrate dev` locally, through git, to `migrate deploy` in your pipeline. Named instances (`npx prisma dev --name myapp`) keep several projects from colliding.
  </Accordion>
</Accordions>

## Recap

The exact checklist, condensed:

1. **Develop locally.** `npx prisma dev` for a zero-setup local Prisma Postgres, or keep your Docker Postgres. Apply schema changes with `npx prisma migrate dev`.
2. **Create the hosted database.** Console **New project**, or `npx prisma init --db`, or `npx create-db@latest`. Copy the connection string.
3. **Update config.** Swap `DATABASE_URL`, run `npx prisma generate`, and store the production URL in your platform's env settings.
4. **Move schema and data.** Fresh start: `npx prisma migrate deploy` plus your seed. With data: `pg_dump -Fc` locally, `pg_restore` over the direct connection, history included.
5. **Validate.** `npx prisma migrate status`, row counts in Studio, one smoke test, then deploy with `migrate deploy` in the pipeline.

The gap between local and production is one connection string wide. Start the local half today with `npx prisma dev`, and when the app is ready for other people, the [Console](https://console.prisma.io) has the hosted half provisioned before your coffee cools.
